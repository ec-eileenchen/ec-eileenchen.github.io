Understanding Credit Card Fraud Detection

Architectural Diagram: From Concept to Implementation

This section details the technical architecture of the credit card fraud detection and education system. It demonstrates how the project's design evolved from an initial high-level concept into a detailed, implemented structure, showcasing the technical decisions made throughout the capstone process.

Initial Architectural Vision

The initial design specification outlined a broad, two-track vision: a machine learning pipeline for analysis and an extended user interface for interaction. This conceptual diagram served as a roadmap at the project's outset.

Figure 1. Initial architectural vision for the fraud detection system

Key Components & Rationale:

  • Foundation: The design was centered on processing the IEEE-CIS Fraud Detection Dataset as the single source of truth.
  • Core Workflow: It clearly separated the data processing and model-building phase from the user-facing delivery phase.
  • Ambition: The architecture included an ambitious "Extended User Interactive Feature," initially envisioned as an AI Chatbot, to provide personalized explanations.
  • Technology Stack: It identified a suite of potential technologies (Python, Scikit-learn, Streamlit, OpenAI) that would be explored.

This initial architecture was crucial for planning but was refined significantly through the implementation process.

Final Implemented Architecture

The final architecture reflects the realities of development, stakeholder feedback, and the strategic decisions made to ensure a successful, high-quality deliverable. The updated diagram provides a clear, expert-level view of how the system is actually constructed.

Figure 2. Final implemented architecture of the fraud detection system

Key Components & Implementation Details:

Machine Learning Pipeline (The Analytical Engine)
  • Data Source & Preprocessing: The transaction.csv and identity.csv files were merged on TransactionID. A rigorous preprocessing pipeline was implemented using Pandas and NumPy to handle missing values, encode categorical variables (like ProductCD and card_type), and standardize numerical features. A time-series split was used for validation to prevent data leakage.
  • Model Training & Validation: Three models (XGBoost, LightGBM, LSTM) were rigorously trained and evaluated. The primary evaluation metrics were Precision, Recall, F1-Score, and ROC-AUC, reflecting the real-world cost trade-offs of fraud detection. LightGBM was selected as the production model due to its superior performance and computational efficiency.
  • Explainable AI (XAI): The SHAP (SHapley Additive exPlanations) library was applied to the LightGBM model to generate global explanations. This process identified and ranked the most important features (e.g., 'Vesta-engineered features,' 'transaction amount') that drive fraud predictions, forming the core analytical insight for the user-facing component.
User Education Pipeline (The Delivery Mechanism)
  • Insights & Content Generation: The technical outputs from the SHAP analysis were translated into clear, non-technical language. This content was prepared in English, Spanish, and Chinese to meet the accessibility needs of the stakeholder's community.
  • Web Application: A static HTML/CSS/JavaScript website was built from scratch to host this content. Key implemented features include:
    • A mobile-first, responsive design to ensure accessibility for users primarily on smartphones.
    • A client-side multi-language engine that dynamically swaps content without requiring a server.
    • Clear sections explaining fraud detection factors and user rights, directly derived from the model's explainable AI insights.

Evolution of the Architecture: A Reflective Analysis

The journey from the initial vision to the final architecture involved several key pivots and refinements:

  • De-scoping for Focus: The most significant change was the removal of the Chatbot and Streamlit dashboard. Based on expert advice, this ambitious scope was identified as a risk. The time was re-allocated to deepening the model analysis and SHAP implementation, which strengthened the core intellectual contribution of the project.
  • From Generic to Specific Tools: The initial diagram listed many potential libraries. The final architecture reflects the actual tools used to deliver the working product. For example, Plotly and Dash were used for exploratory data analysis but were not needed in the final web deployment, which used a custom, lightweight frontend.
  • Clarified Data Flow: The final diagram makes the critical "hand-off" point explicit: the "Key Insights & Feature Importance" generated by the SHAP analysis are the direct input for the "Insights & Content Generation" phase. This clarifies that the webpage is not a live model but an educational tool based on the model's static analysis.
  • Stakeholder-Driven Design: The emphasis on multi-language support and mobile-friendly design in the final architecture was a direct result of feedback from the Financial Empowerment Network (FEN), ensuring the tool would be practical and accessible for its intended audience.

This architectural evolution demonstrates a mature approach to software and data science projects: starting with a bold vision and making pragmatic, evidence-based decisions to deliver a robust, high-value final product.
